# CRAD demo data

This folder seeds fictional CRAD workflow examples into the existing
consolidated SMS2 database (both `sms2_*` and `crad_*` tables). Select the
database configured for the application before importing; `sms2_db` is the
local development name, while a host may assign a different database name.
These scripts do not select or create a database, create a separate CRAD
database, or change application roles, permissions, PHP files, or existing
table definitions.

The batch identifier is `CRAD_DEMO_2026_01`. The only persistent DDL is
`CREATE TABLE IF NOT EXISTS crad_demo_seed_records`, the ID registry used for
safe repeats and batch-scoped reset. Each stage recreates its small temporary
lookup tables because hosting-panel imports may use a new connection for every
file. Later stages resolve generated IDs through the registry and stable demo
keys; they do not assume IDs generated by an earlier import session.

## SQL files and exact import order

Import each file as a **separate operation**, in exactly this order. Each file
is below 40 KB; no SQL statement or logical multi-row insert is split across
files. All data-writing stages check their prerequisites and commit only their
own transaction. `12_demo_analytics.sql` is read-only validation.

The expected total is **616 batch-registered records** after the final stage.
These estimates are the number of newly registered demo rows from a clean
baseline; re-running a completed stage should reuse its registry keys and not
increase the total.

pin a database-server version, and a live HostForge import was not available for
reproduction. The target must be MySQL/MariaDB-compatible and expose the
assignment columns checked by stage 03.

## Backup, import, failure recovery, test, reset, verify

Use a **disposable clone** of the exported consolidated `sms2_db` for testing.
The supplied deployed export was inspected as a schema/workflow source; it was
not imported into or changed. Do not experiment on the live database.

1. Back up the complete consolidated application database and record baseline
   counts for `sms2_users`, `sms2_student_profiles`, `crad_research_groups`,
   `crad_title_approvals`, and the process tables listed below. Keep the backup
   outside this demo folder.
2. Restore that backup to a disposable MySQL/MariaDB instance, retaining the
   application-configured database and both the `sms2_*` and `crad_*` tables.
3. Import `00_demo_setup.sql`, then import files `01` through `12` **one at a
   time** in the exact sequence above. Use a client/panel that stops on the
   first SQL error; do not use a “continue on error” option. For a command-line
   import in `cmd.exe`, run one command per file:

   Select the application's existing consolidated database in phpMyAdmin
   before each file import. For command-line imports, explicitly pass that
   configured database name; replace `YOUR_CONSOLIDATED_DB` with the name from
   the application environment (for example, HostForge's assigned name):

   ```bat
   mysql.exe --batch --user=YOUR_DB_USER --password --default-character-set=utf8mb4 --database=YOUR_CONSOLIDATED_DB < database\crad_demo\00_demo_setup.sql
   mysql.exe --batch --user=YOUR_DB_USER --password --default-character-set=utf8mb4 --database=YOUR_CONSOLIDATED_DB < database\crad_demo\01_demo_users.sql
   ```

   The SQL intentionally has no `USE sms2_db` statement, so it cannot silently
   switch away from the selected application database.

   Continue with the next filename only after the current import exits
   successfully and displays its completion result. Use the hosting panel's
   Import action once per file when importing through the panel.
4. If a file fails, **stop immediately**; do not import any later file. Fix the
   cause, then verify that the failed file's transaction rolled back. If the
   connection remains open, issue `ROLLBACK`; otherwise closing the session
   rolls back its uncommitted InnoDB writes. Re-import the failed file and
   resume with the next file only after success. If rollback cannot be
   confirmed, run `99_demo_reset.sql` and restart at `00_demo_setup.sql`.
   Prerequisite failures intentionally stop the import rather than producing
   partially connected later-stage records.
   If the panel displays only a generic failure message for
   `03_demo_assignments.sql`, run this read-only check in the selected
   application database and compare the output with the expected 117 users,
   16 groups, and 80 member rows:

   ```sql
   SELECT table_name, COUNT(*) AS demo_records
   FROM crad_demo_seed_records
   WHERE batch_id = 'CRAD_DEMO_2026_01'
     AND table_name IN (
       'sms2_users','sms2_student_profiles','crad_research_groups',
       'crad_research_group_members'
     )
   GROUP BY table_name
   ORDER BY table_name;

   SELECT table_name, column_name
   FROM (
     SELECT 'crad_research_coordinator_assignments' AS table_name,
            'confirmation_status' AS column_name
     UNION ALL
     SELECT 'crad_research_adviser_assignments','confirmation_status'
     UNION ALL
     SELECT 'crad_research_assignment_cycles','coordinator_confirmed_at'
   ) required
   LEFT JOIN information_schema.columns actual
     ON actual.table_schema = DATABASE()
    AND actual.table_name = required.table_name
    AND actual.column_name = required.column_name
   WHERE actual.column_name IS NULL;
   ```

   The first query should show 117 `sms2_users`, 80
   `sms2_student_profiles`, 16 registered placeholder groups, and 80 registered
   members. The second query should return no rows. In `03_demo_assignments.sql`,
   the preflight resultset also lists any missing assignment columns before the
   prerequisite guard prevents the assignment writes. If all checks pass but
   the panel still shows a generic failure, capture the import's SQL error and
   failing statement/line from the panel's details or server error log; the
   generic message alone cannot identify a statement-level cause.
5. After `12_demo_analytics.sql`, its validation result must be
   `CRAD demo prerequisite checks passed`. Check the counts in **Final
   verification checklist** and compare pre-import baseline counts to ensure
   real records remain unchanged.
6. Test with the role accounts below on the disposable clone. For attachment
   workflows, upload fictional PDFs through the application before testing
   previews/downloads; see **Upload limitation**.
7. To remove the demo at any stage, import `99_demo_reset.sql`. It deletes
   registry-listed rows plus later UI-created records only when attached to
   registered demo entities. It never drops/truncates tables or broadly
   deletes records. The empty registry table remains installed.
8. Verify reset completion:

   ```sql
   SELECT COUNT(*) AS remaining_batch_rows
   FROM crad_demo_seed_records
   WHERE batch_id = 'CRAD_DEMO_2026_01';

   SELECT COUNT(*) AS remaining_demo_users
   FROM sms2_users
   WHERE username LIKE 'crad_demo_%';

   SELECT COUNT(*) AS remaining_demo_student_profiles
   FROM sms2_student_profiles sp
   JOIN sms2_users u ON u.id = sp.user_id
   WHERE u.username LIKE 'crad_demo_student_%';
   ```

   All three results should be zero. The registry **table** remains installed
   and empty. Re-run the same baseline count queries and compare with the
   saved pre-import results before retiring the clone.

The seed is repeatable: registered rows are reused by stable batch keys.
Before inserting accounts, it stops on a username/email collision with an
unregistered account rather than adopting or deleting a real user. Proposal
and official group numbers follow the existing ID/year patterns and are
resolved from the IDs actually created in the target database.

Use this SQL for the count and group-size checks:

```sql
SELECT table_name, COUNT(*) AS demo_records
FROM crad_demo_seed_records
WHERE batch_id = 'CRAD_DEMO_2026_01'
GROUP BY table_name
ORDER BY table_name;

SELECT g.group_number, g.group_name, COUNT(m.id) AS member_count
FROM crad_demo_seed_records r
JOIN crad_research_groups g
  ON r.table_name = 'crad_research_groups'
 AND r.record_id = g.id
LEFT JOIN crad_research_group_members m
  ON m.research_group_id = g.id
WHERE r.batch_id = 'CRAD_DEMO_2026_01'
GROUP BY g.id, g.group_number, g.group_name
ORDER BY g.group_number;

SELECT c.status, COUNT(*) AS assignment_cycles
FROM crad_demo_seed_records r
JOIN crad_research_assignment_cycles c ON c.id = r.record_id
WHERE r.batch_id = 'CRAD_DEMO_2026_01'
  AND r.table_name = 'crad_research_assignment_cycles'
GROUP BY c.status
ORDER BY c.status;
```

## Upload limitation and testing boundary

The SQL can seed workflow rows and metadata, but cannot place files in the
application's upload directories. Chapter and manuscript rows therefore use
fictional filenames, zero-byte metadata, and demo subdirectories; their
download/preview links will not have a corresponding PDF until a tester uploads
fictional files through the normal UI. Do not represent the placeholder paths
as working document downloads. The SQL reset removes database records only; it
does not delete uploaded files. Inspect the exact demo upload paths manually
before any filesystem cleanup.

This package was checked against the supplied export's schema and the v3
workflow code. A schema-only clone was tested on MariaDB 10.4.32 with a clean
import of stages `00`–`12`, a repeat import, and reset `99`. A live HostForge
import, browser login, dashboard visibility check, notification click, or
role-by-role next-action test has **not** been performed here. Perform those
checks only on the disposable clone described above; do not treat the isolated
SQL test as evidence that the deployed UI has been exercised.
